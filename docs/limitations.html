Honest limitations

SoftwareX-style software papers should state failure modes clearly. ChromeRAG optimizes for RAG ingest quality on real HTML — not for beating every extractor on every page type.

JavaScript empty shells

If a site ships a near-empty HTML document and fills content only after JS runs, ChromeRAG will extract little or nothing. It does not launch a browser. Render first (Playwright / your crawler), then call chromerag extract. The CLI and API now emit an explicit WARNING: when input HTML looks like a JS shell or is otherwise thin, so you can verify the pipeline that serves HTML to ChromeRAG (--fail-on-thin exits 3 if you want hard failure).

Scoreable filter in benchmarks

Latest public run: 373 listed, 277 fetched, 250 scoreable, 27 thin. Scoreable means the input HTML has at least 50 main-content 5-gram anchors; the rule never looks at any extractor's output, so every tool is averaged over the same tool-independent set. Revalidation of the 27 thin pages finds 7 JS-shell-like inputs, 1 other thin DOM, and 19 pages with visible text but too few main/article anchors to score—so “thin” is a hygiene label, not “always an empty SPA.” Means over all 277 fetched pages are published alongside (ChromeRAG coverage Fbal 0.752, Trafilatura 0.698). Separately, chromerag extract warns on JS-shell / thin HTML so callers can verify their fetch pipeline.

Heuristic anchors

Recall / noise metrics use structural HTML regions (main/article vs nav/footer), not hand-labeled gold spans. Optional LLM rubric scores are secondary only.

Scope

HTML → Markdown for RAG. Not PDF/Office conversion (see MarkItDown). Not a hosted crawl API.
